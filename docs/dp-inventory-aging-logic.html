DP 库龄计算方案

逻辑库龄：业务操作如何影响库龄

方案版本：5.6.0（继承库龄仅存在于「库存分配」场景） 目标仓库：第三方仓海外仓 更新：2026-08-26

1 方案定位

按 「层级仓 × SKU × 批次」 三个维度，用 FIFO（先进先出） 推演出每一批货的剩余数量和库龄天数，回答业务问题：现在躺在仓库里的货，各自压了多久了？

三条核心规则，记住这三条就够：
① 库龄 = 目标日 − 批次入库日（用业务时间，不是系统写流水的时间）；
② FIFO：出库时总是先扣最早入库的那批；
③ 库龄「继承」只发生在「库存分配」一个动作——其他任何入库都是重新计龄，任何出库都是消耗最老批次。

一句话区分「继承」与「重算」：货物理上没动、只是改了记账层级，库龄要继承；货真的进仓/出仓了，库龄就重算/消耗。

2 业务操作如何影响库龄（核心）

库龄不是事后「算」出来的玄学，而是由你在系统里做的每一个操作决定的。下表把「操作」和「库龄后果」一一对应：

业务操作系统里发生了什么库龄后果业务类型
采购入库 / 盘点入库 / 退货入库 / 维修入库 / 加工入库 / 移除入库 / 其他入库货物到仓上架🆕 新起批次，库龄从到货日算起1/2/4/5/6/7/100
调拨入库货从 A 仓运到 B 仓🆕 新起批次，按 B 仓到货日重新计龄（不继承源仓）3
销售出库 / 调拨出库 / 盘亏 / 加工出库 / 其他出库货物离开仓库⬇️ 先出最老，FIFO 扣减最早入库的批次-4 / -3 / -2 / -6 / -100
库存分配（IA）同一仓库内，层级 A → 层级 B 转移，货没动🔄 继承库龄（唯一继承场景），沿用原批次日期1000

为什么「调拨入库」不继承、而「库存分配」继承？调拨是跨仓库搬运，货到了新仓就是新仓的「新可用库存」，库龄从头算；库存分配是同一仓库内改归属标签，货没挪窝，只是换了记账层级——如果重新计龄，等于把旧库存「洗白」，掩盖真实滞销。详见第 3、4 节。

3 库存分配 —— 唯一继承库龄的场景

业务场景是什么

把一批货从「公共层级」划一部分到「分销_FR_SPL」层级。货还放在同一个仓库的同一批库存里，物理位置、SKU、数量都没变，变的只是「这批货记在哪个层级名下」。

为什么必须「继承」库龄，不能重新计龄

假设不继承：一批货 3 月入库，放了 5 个月；8 月做一次「库存分配」移到分销层级。如果按 8 月分配日重新计龄，这批货的库龄瞬间从「150 天」归零成「0 天」——系统会把它当新货卖，掩盖了真实滞销，库龄报表严重失真。

正确做法：分配后，目标层级承接的货沿用它在原层级时的入库日期，该多少天还是多少天。

继承机制（数据上怎么体现）

一次库存分配会写两条流水，用同一个分配单号（IA 单号）串起来：

【层级 A 出腿】private_log: business_type = 1000, change_qty = -200, private_id = A → A 层级的 FIFO 队列扣掉最老的 200 件（例：100 件是 6/15 入的、100 件是 7/1 入的） 【层级 B 入腿】private_log: business_type = 1000, change_qty = +200, private_id = B → B 层级新增的 200 件，批次日期照抄刚才 A 扣掉的那两批：6/15(100)、7/1(100) → 而不是用「分配日」当批次日期
A 层最老批次
6/15 × 100 / 7/1 × 100 → 分配单 IA → B 层继承批次
6/15 × 100 / 7/1 × 100 → 库龄不变
该 150 天还是 150 天
关键点：行业内通常叫「层级库龄 / 逻辑库龄继承」。记住一句话——分配是「改标签」不是「搬货」，标签变了，货的年龄不能变。

4 调拨为什么「不继承」库龄

调拨 = 跨仓库搬运。货从 A 仓发货（-3 调拨出库），在途一段时间，到 B 仓收货（3 调拨入库）。

【源仓 A】发货：business_type=-3，FIFO 扣掉 A 仓最老批次 200 件 （A 仓这 200 件的库龄到这里「终结」） 【在途】... 2-3 周 ... 【目标仓 B】到货：business_type=3，按 B 仓到货日 inbound_time 新起一批 200 件 （B 仓这 200 件的库龄从「到货日」开始算，0 天起）
业务含义：对 B 仓而言，到货的是一批「新到可用库存」。库龄口径是分仓独立计算——B 仓从这批货进自己仓库起算它的年龄。在途时间不是「丢失」，而是 B 仓库龄的天经定义。这也是为什么调拨入库在数据上按普通入库一样处理，不需要关联源仓批次做继承。

5 技术落点：数据取数与 FIFO 推演

本节面向数据/开发，业务同学可跳过，只看结论即可。

5.1 数据源与业务时间锚点

层级库存变动的唯一数据源是 t_wms_inventory_private_log（层级库存流水表）。但它的 create_time 是系统写流水的时刻，比真实业务时间晚 15-40 小时，不能用来算库龄。

业务时间必须回表取：入库取单据的 inbound_time（上架时间），出库取 outbound_time（发货时间）。关联方式：入库 bound_no → t_wms_inbound.inbound_no，出库 bound_no → t_wms_outbound.outbound_no。

5.2 出库流水 bound_no 大量为空（不是数据缺漏）

销售/调拨出库是「先占用、后发货」两段式，流水分多批写：

阶段inventory_typechange_qtybound_no对库龄
占用·扣可用1（可用）负空跳过（内部转移）
占用·加锁定2（锁定）正空跳过（内部转移）
发货·扣锁定（真出库）2（锁定）负有值FIFO 消耗
释放·退订2→1负→正空跳过（内部转移）
甄别真出库的唯一稳定口径：in_out_type='2' 且 bound_no 非空。占用/释放是「可用↔锁定」内部转移，总量不变，必须跳过，否则库存被提前扣掉、库龄整体偏新。

5.3 库存分配（IA）在数据上的识别

库存分配不走标准在库/在途出库模型，特征如下：

  • business_type = '1000'（INVENTORY_ASSIGN）；
  • 一次分配是两条流水，同 business_no（= 分配单号 assignNo）：一条 change_qty<0（from 层级出）、一条 change_qty>0（to 层级入）；
  • 两条都在同一仓库内，仓库总量不变，只变层级。

5.4 FIFO 推演伪代码

// batch_queue: Map<(wh_id, private_id, sku_id), Deque<Batch>> 按批次日期升序 // assign_consumed: Map<assignNo, [批次]> 库存分配的「出腿消耗」缓存 // 1. 初始化：起始日快照作为各层级初始批次（批次日期用起始日前一天近似） // 2. 逐笔推演（按 biz_time 升序，同时刻入在前出在后） FOR EACH doc IN docs: IF doc.business_type == '1000': // —— 库存分配（唯一继承场景）—— IF doc.change_qty < 0: // 出腿：from 层级 FIFO 消耗 assign_consumed[doc.business_no] = FIFO_deduct(from_key, |change_qty|) ELSE: // 入腿：to 层级继承 from 消耗的批次 FOR EACH batch IN assign_consumed[doc.business_no]: batch_queue[to_key].push({date: batch.date, qty: batch.qty}) ELSE IF doc.in_out_type == '1': // —— 普通入库（含调拨入库）—— batch_queue[key].push({date: doc.inbound_time, qty: doc.change_qty}) // 新起批次 ELSE IF doc.in_out_type == '2' AND doc.bound_no 非空: // —— 真出库 —— FIFO_deduct(key, doc.change_qty) // 消耗最老批次 // 其他（占用/释放/调拨出库的占用腿等）：一律跳过 // 3. 算库龄：对每个 (wh, private, sku) 的每个 batch，aging = 目标日 − batch.date

6 关键风险与交付

风险1：误把「库存分配」当普通出库+入库。如果数据组不识别 business_type=1000 的双流水继承关系，分配的货会被「出库一条 + 重新入库一条」拆开重算，库龄被洗白。这是本方案最核心的一处，务必第一优先验证。
风险2：占用/释放混入真出库。销售/调拨的「占用、取消释放」流水 in_out_type 也是 '2'，仅靠方向判断会误扣库存，必须用 bound_no 非空兜底。
风险3：SPL中转仓层级缺失。SPL中转仓（wh_id=68）目前仅配「公共」层级，若要拆分中转仓库龄，需先完成层级初始化。
风险4：初始库存批次日期为近似值。起始日库存统一按「起始日前一天」作为批次日期，对 180 天+ 长库龄的分类无影响，精确批次需从历史快照恢复。
