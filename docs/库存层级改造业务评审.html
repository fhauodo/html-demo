库存的「归属改造」：这次改了什么、需要您确认什么

为什么要改（改造背景）

目前库存层级同时存在展示问题和数据存储结构问题：树上看到的归属，和库里真正记的归属对不齐；一个层级还可以被多个仓"借用"。这样的地基撑不住后面的库存模块需求。为更好满足后续能力开展——例如逻辑库龄计算、层级间分配库存等——需要先把库存层级优化到位。

展示页面上看不清、选不准
  • 整棵树顶上只有「公共」，仓库被压在第二层，看不出「这个层级属于哪个仓」
  • 父层只是分组展示，点进去不能汇总子层库存，对账和看总量都费劲
  • 仓库层和实际存货层混在下拉里，选层级时容易选到不能存货的节点
存储归属对不齐、身份不稳
  • 仓库和层级是多对多绑定：同一层级可以被多个仓借用落货
  • 层级身份主要靠名称，编码可空可重复；改个名就可能对不上历史单据
  • 已删层级仍挂着库存和流水，账面和树对不齐
后续：逻辑库龄计算
库龄要按「仓库 + 层级」把入库时间串起来。归属不清、编号不稳，同一批货就算不准、也对不齐数仓取数。
后续：层级间分配库存
仓内渠道之间调库存（公共池分到店铺、售后回良等），必须先分清「从哪个层级到哪个层级、是否同仓」。现在可以跨仓借用层级，分配口径会乱。
这次改造要做的：把层级的展示树和存储归属对齐——每个仓库有自己名下的层级，层级只能挂在它自己的仓库下。先把地基打稳，后面的库龄、分配、对账才能接着做。

这次改了什么（4 类改造点）

改造点 1｜层级"家庭关系"变清晰

现在顶层只有「公共」一个；改后顶层多出 25 个仓库和「公共」并列，另外加一个只管展示的「全部」来兜底分组。

现在的结构（3 层）
  • 公共 唯一顶层
    • 德国万邑通仓 仓库
      • 德国万邑通_公共 库存
      • 售后_EU 库存
    • 英国谷仓 仓库
      • 英国谷仓_公共 库存
      • Shopify_UK 库存
    • … 共 25 个二层、109 个三层
改造后的结构
  • 全部 虚拟分组
    • 公共 跨仓池
    • 德国万邑通仓 仓库
      • 德国万邑通_公共 库存
      • 售后_EU 库存
    • 英国谷仓 仓库
      • 英国谷仓_公共 库存
      • Shopify_UK 库存
虚拟分组「全部」 「公共」跨仓池 仓库层（挂哪个仓） 实际库存层
对业务操作的影响
  • 库存层级页（看树）：树顶多出一个「全部」分组；「公共」从唯一顶层降到与各仓库并列的二层，一眼能看出「这个仓下面有哪些层级」。
  • 层级库存页（查数）：选某个二层仓库层（如「英国谷仓」）时，会汇总展示其下所有三层（英国谷仓_公共、Shopify_UK…）的库存——以前只能看单层，现在点仓库层就能看整仓合计。
  • 和后面改造点的区别：层级库存可以选二层查数；但调拨、入库、分配等操作类页面不能选二层落账，只能选「公共」或三层实际库存层（见改造点 4）。

改造点 2｜新增 / 编辑 / 删除的按钮规则收紧

按钮现在改后
新增随便哪个节点都能点"新增"往下加「公共」下禁建子级；三层（如「德国万邑通_公共」「售后_EU」）下禁建四层。只有「全部」和仓库层能新增
编辑名称、能否存货都能改仓库层（「德国万邑通仓」「英国谷仓」…）的名称、上级、能否存货全部只读，跟着仓库走
删除只查"有没有子层级"还要查"有没有库存、有没有被单据引用"；有货的被拦
能否存货开关手动勾由层级类型自动定，业务不用再管
对业务操作的影响
  • 想自己在「公共」下面加仓库层：不行。「公共」下禁建子级，仓库层只能随仓库主数据新增/联动出现。
  • 想在某个三层下面再加一层：不行。三层已是实际库存层，禁建四层；要加业务层级，只能在对应仓库层下新增。
  • 想改「德国万邑通仓」这层级的名字：不行。仓库层名称、上级、能否存货全部只读，须去仓库列表改名，层级页自动同步。
  • 想删掉还有货或被单据引用的层级：系统会拦。删除前会查子层级、库存量、调拨/分配/出入库等引用，有货或有引用删不掉。

改造点 3｜仓库增删改，自动联动层级

仓库操作改后联动
新增仓库自动同步建一个同名"仓库层"，否则会出现"有仓库但没层级"
仓库改名同步改层级名，否则层级还叫旧名、在层级页找不到
仓库停用/删除先检查下面还有没有层级、有没有库存，再处理
对业务操作的影响
  • 仓库列表 · 新增仓库：保存后系统自动建同名「仓库层」，业务不用再去层级页手工补一层；若没自动出现，说明联动异常需提工单。
  • 仓库列表 · 改名：层级页里对应仓库层名称同步变更；以后在各页面按新名字找层级即可，不用两边各改一次。
  • 仓库列表 · 停用/删除：若该仓下还有层级或库存，会先被拦住；须先把货挪走、子层级处理好，才能停/delete。

改造点 4｜所有"选层级"的操作页：二层仓库层只能看、不能选

核心规则：「德国万邑通仓」「英国谷仓」这类二层仓库层，在下拉里只当分组展示，不能作为收货/调入/调出/扣减的目标层级。能选的是跨仓「公共」和各仓库下的三层实际库存层（如「英国谷仓_公共」「Shopify_UK」「售后_EU」）。

和「层级库存」的区别：层级库存页可以选二层查汇总；下面各模块是操作落账，二层仓库层一律不可选。

放宽心的一点：真正"一个层级被两个仓同时塞着货"的很少——抽查下来，一个层级散到别的仓只有个位数到十几行量，不是大规模迁移。真正的活，在"怎么承接这些借来的层级"这件事上。

  • 运营侧：需确认每个平台仓是「继续走公共」还是「新建仓_公共等业务层级」（决策 07 专讲亚马逊）；定完后才能恢复正常的选层级、落库存。
  • 和改造点 4 的关系：承接方案定好后，这些仓的操作页也会遵守同一规则——不能选二层仓库层，只能选名下的三层或（若业务确认）公共池。

01
12 个第三方仓的层级，怎么承接？
高优先 · 影响最大
背景：澳洲亚马逊仓、Lazada马来海外仓、Shopee马来西亚官方仓、德国亚马逊仓等 12 个第三方/售后仓自己没建层级，靠借用「德国万邑通」「英国谷仓」名下层级落库存（见上一节）。改成"一个层级只属于一个仓库"后，它们会没有可选层级。
方案 A 给每个第三方仓复制一套自己的层级。工作量大、一次性，但彻底合规，符合"一仓一层级"大原则。 推荐
方案 B 保留"共享层级"特例，第三方仓继续借用。上线快，但违背大原则，要在全链路留一套特例逻辑，长期是个坑。
方案 C 第三方仓改用「公共」承接，不再用借来的明细层级。取决于业务上这些仓是否只需记公共池——需和运营确认。
为什么必须现在定：不定的话，第三方仓的入库和库存同步会全部卡住，这个改造没法上线。
定了以后，日常操作怎么变
  • 方案 A：各第三方仓有自己的三层可选，调拨/入库/同步按本仓名下层级落账，和自营仓操作一致。
  • 方案 C：这些仓统一落「公共」，操作页里选公共即可，但按站点/按仓看库存、算库龄会混在一起。
  • 方案 B（不推荐）：继续借用，操作习惯几乎不变，但长期留特例，和「一仓一层级」目标冲突。
02
4 个已删层级，挂着的库存和单据怎么清理？
中优先
背景：「分销_2B」「MKT_EU」「英国不良品仓」「法国不良品仓」4 个层级早已删除，但至今还被引用——库存 224 行、流水 843 行、分配明细 396 行、其他出入库 54 行（其中 MKT_EU 占大头）。改造后，这些早已删除的层级仍挂着库存和单据，会留成"对不上账"的残留，需业务定清理方式。
方案 A 按业务归属合并到现有有效层级。需业务指出每批数据各自合并到哪个层级。 推荐
方案 B 新建"历史归档层级"承接，保留但与正常库存隔离。
方案 C 本期暂不处理、维持现状。风险：这些已删层级的历史数据会一直挂着，账面始终对不齐。
需要业务提供"各自合并到哪"的映射意见，否则开发只能选方案 B 先归档。
03
「公共」层级的未来定位？
高优先 · 牵扯 4,389 行
背景：公共池现有 4,389 行库存，调拨收货"选公共"的场景全依赖它。改造后「公共」从"唯一顶层"变成"和 25 个仓库并列的节点"——它是继续当跨仓公共池，还是逐步拆回各仓？
方案 A 「公共」保留为跨仓公共池，继续允许作为收货/调入目标。改动最小，调拨逻辑影响小。 推荐
方案 B 逐步取消公共池，把 4,389 行按仓拆回各自仓库层级。更彻底，但迁移工作量大、要逐个仓定映射。
「公共」是新结构里唯一"不属于任何仓库"的池子，它的定位会影响调拨收货"选公共"这个用法还留不留，建议先定方向。
定了以后，日常操作怎么变
  • 方案 A（推荐）：调拨/备货「收货层级选公共」继续可用；4389 行存量不动，业务无感迁移。
  • 方案 B：逐步取消公共池，以后收货/调入不能再选公共，须指定到各仓三层；4389 行要按仓拆分迁移，工作量大。
04
25 个存量二层 + 占位节点，下线的节奏？
中优先
背景：25 个存量二层里，10 个还挂 292 行库存（德国万邑通退货仓 89、亚马逊仓 65、shokz全球-泰国菜鸟仓 49、Anchanto韩国仓 35、KR-韩国菜鸟仓 31、英国谷仓 11、新加坡待维修仓 11、筋斗云 1），其余 15 个是空的。另有一个占位节点「(请选择公共层级)」无库存无子节点。
方案 A 空的下线、有库存的先冻结观察、占位节点一起下线。 推荐
方案 B 全部先冻结，下个周期再清。
方案 C 一次性全部下线，把 292 行库存腾挪到新结构。快，但要先搞定腾挪目标。
建议优先处理；10 个有库存的二层若仓促下线会出负库存，需和仓库确认。
05
15 个售后层级，在新结构里放哪？
低优先 · 但别漏
背景：现有 15 个"售后"层级独立存在，涉及顺丰售后查询等入口。新结构下，售后层级归属哪个仓库、挂在第几层，需要明确。
方案 A 售后层级作为对应仓库的"实际库存层"之一，归属到该仓下。 推荐
方案 B 售后层级单独成组，不归任何仓（保留现状的独立语义）。
方案 C 售后层级合并进普通层级，不再单独区分。
如果售后查询强依赖"售后"这个类型，建议选 A 或 B 保留类型；选 C 则要先确认售后查询不受影响。
06
数据组 / 数仓的取数，会不会被这次改造打断？
中优先 · 影响数仓取数
背景：数据组做「逻辑库龄」，取数靠层级编号（level_id）把流水和库存串到层级上。好消息：这次改造可以让层级编号保持不变——只新增一个「全部」虚拟节点、把公共和各仓的父级从「公共」改挂到「全部」下。编号不动，数仓的历史流水/快照就能照旧关联；唯一要同步的是层级树的拓扑变了。
方案 A 层级编号保持不变，只改父级归属 + 新增「全部」节点。数仓历史取数不受影响，只需同步新的树结构和字段口径。 推荐
方案 B 层级编号重新生成，则必须提供「旧编号→新编号」映射表给数仓重刷历史，工作量大、风险高，不划算。
方案 C 数仓改用「仓库+层级名称」关联，不再依赖编号。名称有重名风险，需数据组评估。
层级编号是否保持，直接决定数仓要不要重刷历史。方案 A 改动最小，确认后数仓只需跟着新的树结构取数即可。
07
亚马逊仓的库存层级，怎么管？
高优先 · 平台/FBA 仓
背景：澳洲亚马逊仓、英国亚马逊仓、德国亚马逊仓等约 8 个亚马逊 FBA 仓，目前自己名下没建层级——部分库存落在跨仓「公共」池（公共池里约 930 行来自平台/FBA 仓），部分靠借用其他仓的明细层级落货。改造后每个仓都要有明确归属：亚马逊各站点是继续记「公共」，还是各自新建「仓_公共」等业务层级？这会影响 FBA 库存同步落点、逻辑库龄按站点拆分，以及后续层级间分配能不能按站点管。
方案 A 亚马逊仓继续用「公共」承接，不单独建层级。改动最小，但各站点库存混在一个跨仓池里，按站点看库龄、做对账、做分配都拆不开。
方案 B 各亚马逊仓新建自己的层级（如「英国亚马逊仓_公共」），公共池里属于该仓的库存迁入名下。符合"一仓一层级"，可按站点独立管理，但需一次性建层并定迁移映射。 推荐
方案 C 分站点定：有独立运营、需单独看库存/库龄的站点建新层级；暂只记总量、不需拆分的站点继续走「公共」。灵活，但要逐个站点确认并留清单。
和决策 01（第三方仓承接）、决策 03（公共池定位）相关：若选 A，公共池会长期承担 FBA 库存；若选 B/C，需同步定各站点存量从公共迁出还是保留。建议运营按站点使用情况一起定。
定了以后，亚马逊日常操作怎么变
  • 方案 A 继续公共：FBA 同步、入库仍选「公共」落账；英/德/澳等各站点库存混在一个池，层级库存、库龄、分配按站点拆不开。
  • 方案 B 各站自建层级：每个亚马逊仓下有自己的「仓_公共」等三层，同步/入库落到本仓层级；操作页仍不能选二层仓库层，要选其下三层。
  • 方案 C 分站点：重点站点自建、其余走公共；操作规则同上，但不同站点规则不一致，培训和导入模板要分开维护。
